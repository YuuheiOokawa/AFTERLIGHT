# PostgreSQLデータモデル

backend/schema.sqlはプロトタイプのローカル保存とは別の、製品サーバー用参照DDL。サービス層で必要なトランザクション・権限を実装しなければDDLだけで完成しない。

## 関係
player 1:N player_unit / player_equipment / party / battle / gacha_draw。
party 1:N party_slot、slotは所有unitを参照。
unit_master 1:N player_unit、equipment_master 1:N player_equipment。
banner 1:N banner_rate、banner 1:N gacha_draw、draw 1:N draw_item。
guild 1:N guild_member、guild 1:N guild_contribution。friend_edgeは双方合意、blockは片方向。

## テーブル一覧
|テーブル|役割／制約|
|---|---|
|player|公開名、状態版、作成日時|
|wallet|player×currencyの残高、非負、version|
|currency_ledger|変更前後、差分、理由、ref_id、UNIQUE取引|
|item_master / player_item|素材の定義、非負在庫|
|unit_master / player_unit|役割、レア度、所有体レベル、系統、絆|
|equipment_master / player_equipment|装備、+20、ロック、特性、所有者|
|unit_equipment|装備枠、1装備を複数ユニットに付けない|
|party / party_slot|編成名、5枠、同unit重複不可|
|chapter / quest / quest_progress|12章、ステージ、初回受取|
|story_choice|章選択、同じ選択点に1値|
|battle / battle_action|固定版、乱数seed、状態、行動seq|
|banner / banner_rate|有効期間、費用、確率の版|
|gacha_pity|同系統連続未SSR回数、行ロック対象|
|gacha_draw / gacha_draw_item|確定抽選履歴、演出キー|
|idempotency|player×route×key、body hashと応答|
|friend_request / friend_edge / player_block|申請・双方向関係・遮断|
|guild / guild_member / guild_contribution|役職、週、ノードと貢献|
|arena_season / arena_match / arena_rating|週、相手、結果、正規化snapshot|
|purchase_receipt / mailbox / audit_log|一意購入、配布、監査|

## 所有整合性
party_slotのplayer_idとparty/player_unitのownerを複合外部キーで一致させる。unit_equipmentもunitとequipmentが同じplayerになるよう複合参照。friend_edgeはlow_id<high_idの順で一組だけ保存。guild_memberのplayer_idはUNIQUEなので同時所属は一つ。

## サービス層で守る規則
確率合計100%は公開時検査し、有効期間はサーバー時刻で判定。ギルド30人、フレンド100人、装備種とslotの一致、助っ人の利用、素材ロック保護、週報酬はトランザクション内検査が必要。DBのCHECKは単純な値範囲のみ。状態更新後のwalletとledgerは同時commitする。

## 索引と保存
battle(player_id,created_at)、ledger(player_id,created_at)、draw(player_id,created_at)、guild_contribution(guild_id,week_id)に索引。gachaと購入履歴は監査のため削除ポリシーを別途決める。戦闘actionは保持期間後に圧縮アーカイブ、集計値は残す。ログ保存期間は運用・プライバシー方針を決めて設定し、ここで法定期間を断定しない。

## 移行
schema.sqlを初期参照にし、実際はバージョン付きマイグレーション管理。マスタversionはクライアントと戦闘に保持。既存battleは開始時の版で最後まで進める。ユニット調整時は旧版復帰と補填台帳を用意する。
